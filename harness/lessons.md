### 2026-09-23 — an unpinned JDK made every build cold (the real "hour to build")

### 2026-09-23 — a Gradle check could not run at all with the configuration cache enabled
- Symptom: `./gradlew checkCapabilityManifests` failed with `cannot serialize Gradle script object references`. The capability manifest gate is what feeds the Play Data safety answers, and it had never once run successfully under the factory's own build settings.

- Evidence: the cache report trace read `this$0 → Build_gradle$$$result$1$2 → Field action → VirtualProperty actions → Task :checkCapabilityManifests`. - Change made: `checkCapabilityManifests` is now `CheckCapabilityManifestsTask : DefaultTask()` with `ListProperty`, `Property`, `ConfigurableFileCollection` and `RegularFileProperty` inputs and a `@TaskAction`; every provider read moved to configuration time. ### 2026-09-23 — the factory could not express a repeatable purchase at all
- Symptom: the owner described the monetization he actually wants — an in-app shop selling token or credit packs that a user buys repeatedly, e.g. tokens spent on an AI assistant. The billing capability could not represent that. `Entitlements` was a `Set<ProductKey>` of owned things, there was no balance type, and `PlayBillingController` had **no consume call anywhere**. A pack modelled as an owned entitlement is granted once and, because Play requires a consumable to be consumed before it can be bought again, is then unpurchasable forever. We would have shipped a shop where every product can be bought exactly once.
- Root cause: the capability was designed from the shape of one app — "remove ads or unlock a feature" — and then treated as general. That is the same defect class as a hardcoded error message that drifts from its regex: a single case generalised without checking the cases it excludes. The owner had to name it twice: *"у нас завод, а не конкретное приложение"*. The concrete first symptom was the missing `consumeAsync`, but the real defect was the product model.
- Fix class: model the whole mechanic, not the case in front of us.
- Evidence: `javap` against the real `billing-9.1.0` artifact confirmed the API before any code was written — `ConsumeParams.newBuilder().setPurchaseToken(...)`, `ConsumeResponseListener.onConsumeResponse(BillingResult, String)`, `BillingClient.consumeAsync(ConsumeParams, ConsumeResponseListener)`, and `Purchase$PurchaseState` carrying `PURCHASED`/`PENDING`. Thirty-four billing tests then covered the rules without a device, including the two that would have caught the defect: a consumable credits the wallet and is **consumed rather than acknowledged**, and the same pack bought three times credits three times. `:billing:test :billing:assembleRelease` → `BUILD SUCCESSFUL`, **34 tests, 0 failures, 0 errors** across `PurchaseLedgerTest 11`, `FakeBillingControllerTest 8`, `BillingCatalogTest 7`, `WalletTest 6`, `EntitlementsTest 2`.
- Change made: added `Wallet` (spendable balances, with a spend refused rather than clamped), `ConsumablePack` (grant amount, unit, `Fulfillment` of `LOCAL` or `SERVER_COST`), `PurchaseState`/`PurchaseRecord`/`PurchaseOutcome` mirroring Play without importing Android, and `PurchaseLedger`, which holds the settlement rules in testable code: only `PURCHASED` grants; a consumable is consumed; settlement is idempotent per purchase token because Play re-reports an unconsumed purchase on every cold start; a failure grants nothing so it retries. `BillingController` gained `wallet` and `spend()`. `PlayBillingController` gained the consume call, a `BillingStateStore` (a wallet is **not** recoverable from Play, so losing it loses paid-for credit), and a `PurchaseAuthority` seam required only for `SERVER_COST` packs. The fake settles through the same ledger, so fake tests exercise the real rules rather than a parallel implementation that can drift.

### 2026-09-23 — the worker runner reported DONE for work that was never done
- Symptom: a Codex worker (`remoteconfig`) was launched to build a Firebase Remote Config capability, produced **no files at all**, and `node scripts/codex-run.mjs list` reported it as `DONE last=yes`. It was believed. Only because the authoritative capabilities build printed four `PASS` manifests and no `:remoteconfig:` task — the module was absent from the graph — was the truth found: `capabilities/remoteconfig/` did not exist, `settings.gradle.kts` still listed only `:core, :ads, :billing, :telemetry`, and `capabilityModuleNames` was unchanged. The second worker (`capability-integration`) had the same outcome and was reported `BLOCKED(RATE_LIMITED)`.
- Root cause: three independent defects, all in `scripts/codex-run.mjs`.
  1. **Signal never outranked exit code.** `finish()` computed `meta.status = code === 0 ? 'done' : signal ? 'blocked' : 'failed'`, and `status()` used `rec.exitCode === 0 ? 'DONE' : rec.signal ? BLOCKED(...)`. Both branches put the exit code first, so a run diagnosed with any signal but exiting 0 was reported as `DONE`.
  2. **Diagnosis scanned the entire transcript.** `finish()` ran `diagnose(errText + outText)` over the full stdout log and stderr. That text includes the prompt echo and every file the worker read, and the repo's own documents name the keywords — `AGENTS.md` says `RATE_LIMITED`, `harness/dual-agent.md` tabulates `RATE_LIMITED`/`CONTEXT_LIMIT`/`AUTH_ERROR`. So reading the harness caused the runner to claim the harness had failed. `storekit`'s recorded `CONTEXT_LIMIT` has **no limit text anywhere** in its `.err` or `.log` and was a false positive of exactly this kind; the `cap-ads-billing`, `cap-core`, `scaffold-src` and `scripts` runs, by contrast, do contain a real `ERROR: You've hit your usage limit. Upgrade to Pro` line, so not every signal was wrong.
  3. **Nothing checked that a finished worker changed anything.** A `DONE` label carried no evidence, so "the worker said done" was indistinguishable from "the work exists".
- Fix class: order the signal above the exit code, bound what is diagnosed, and never let a status label stand in for evidence.
- Evidence: `remoteconfig.exit.json` read `{"exitCode": 0, "signal": "AUTH_ERROR"}` while `list` printed `DONE` — a direct contradiction between the record and the label. After the fix the same records print `BLOCKED(AUTH_ERROR)` and `BLOCKED(RATE_LIMITED)`, `node --check scripts/codex-run.mjs` exits 0, and the fix immediately caught the second false `DONE` that the old code had hidden.
- Change made: `DIAGNOSE_WINDOW_LINES = 40` and diagnosis restricted to the tail of stderr plus the tail of the log, so the CLI's own error is read without the prompt echo or the documents a worker opened; `finish()` and `status()` both check `signal` first; `harness/lessons.md` records the finding. Sensor debt: a regression check for the classification belongs in `scripts/selftest.mjs`, but that file is owned by a concurrently running worker, so it is deferred rather than written in a conflict.

### 2026-09-23 - an illustrative example was turned into a product strategy

The screen could never have triggered it (it shows a loading state until `loaded`), which is exactly why it survived to a device: no human clicking could reach it, but a test that calls `load()` then `addClass()` reaches it every time. The placeholders and the 12-character floor are *imported* from `slot-economics.mjs` rather than restated, because a second copy of a rule is a second thing to drift.
- Evidence: 19 legs in the new `differentiator contract (sandbox)` section of `scripts/selftest.mjs` drive the real checker against synthetic slots: one fully resolved contract passes with all four proof types resolved, and the rest fail for exactly the reason they exist - a promise left `deferred`, a proof whose named symbol was deleted while `status` still said `shipped`, a `core` promise dropped with no owner words, a proof in a location its type does not allow, a contract naming another slot, evidence citing a document that is not there, and a one-promise contract against the floors. Two of the legs are discriminators rather than defects: the same deferred contract exits 0 under `--allow-deferred` and non-zero without it, which is what proves the flag is a progress read and not a completion, and the artifact leg fails while the status field still says `shipped`, which is what proves the gate reads the artifact rather than the string. All 19 were observed passing, and the pre-existing failure of the shared sandbox was found and fixed by giving this sandbox-dependent section its own sandbox instead of appending it after the `finally` that deletes the shared one.
- Rules this leaves: **a reason list is a contract, and "hard to implement" is a decision for the owner, not a silent omission.** And **the field a status is set in must not be the thing that proves the status**: a `shipped` promise is proved by a file and a symbol that still exist, never by the word `shipped`.

### 2026-09-26 — localizing a slot silently re-scoped the capture journey to the phone's language
- Symptom: `node scripts/media-capture.mjs --slot teacher-gradebook` failed shot-01 on all three attempts with `5 of 5 expected readings are not in the field they name`, naming English readings - `Your class`, `6 students`, `Class average: 68.3%` - while the screen it had just read was Russian: `Один класс`, `6 учеников`, `Средний балл класса: 68,3%`. The message described a broken journey, and the journey was fine. Two other failures were stacked on top: a Samsung Knox policy dialog swallowed attempt 1, and a capture killed by hand left `store/captures/capture.lock` behind, so the next run refused with `BLOCKED` for a pid that no longer existed.
- Root cause: a journey asserts the literal text of the nodes it photographs, and Android resolves those strings against **the device's** language - not the listing's and not the journey's. That dependency did not exist when the slot's captures were first taken, because the app had no `values-<locale>/` directories: every device resolved to the same English strings, so the phone's own language was invisible. Adding eleven locale directories for the store listing silently coupled the capture to the phone, and the owner's phone is Russian, so the journey became one that could not pass on the only device attached. The dependency was already written down - `store/journey.json`'s `_preconditions` says the system language must be English - but prose no program reads is not a precondition, which is this repo's most-recorded failure mode. Two traps made the diagnosis expensive: `getprop persist.sys.locale` read `en-US` on a device whose live framework config was `ru-rRU` (it is the last value written, not the locale in force), and Android 11 has no `cmd locale`, so the per-app override that would have left the phone alone does not exist there and the system language itself has to change and change back.
- Fix class: **a precondition stated in prose becomes a check that runs before the device is touched**, and it must be readable from the state that is actually in force.
- Change made: `scripts/media-capture.mjs` gained `devicePrimaryLanguage()` - which parses `am get-config`, deliberately not `persist.sys.locale` - and `journeyLanguage()`, and `main()` compares them *before* the capture lock is taken, so a mismatch costs no device run at all. A journey may declare its own `"locale"`, defaulting to `en-US`, and the guard believes it in both directions. It is a guard rather than a gate on its own uncertainty: a config it cannot parse is a `NOTE`, never a refusal, because a harness bug must not block a release the way a wrong locale does. `scripts/test-capture-locale.mjs` drives the decision in ten legs, and `scripts/selftest.mjs` runs it as the section *the capture journey runs on a device in the language it reads*.
- Evidence: the recorded A40 line is a test fixture. `config: ru-rRU,be-rBY-ldltr-sw360dp-w360dp-h703dp-...` answers `ru`, and `config: en-rUS,ru-rRU,be-rBY-ldltr-...` answers `en`; the first leg records that the pre-fix implementation, which had no check, let the English journey proceed, and the second asserts the guard now refuses it naming `ru` against `en`. The test was observed failing before it was trusted: the `config: ja` leg failed on the first run because the terminator needed a trailing qualifier, and the fix was then checked against the device's real `am get-config` output including Windows CRLF. The device moved `ru-rRU,be-rBY` → `en-rUS,ru-rRU,be-rBY` by adding English as primary in Settings, leaving Russian in the list behind it.
- Rules this leaves: **localizing an app re-scopes every check that reads its text** - a capture journey, a UI assertion and a screenshot claim all become device-language-dependent the moment `values-<locale>/` exists, and the store listing is what makes that happen. And **a run that depends on the environment must read the environment**; a precondition that lives only in a `_preconditions` array is documentation for a human, not a guard.
