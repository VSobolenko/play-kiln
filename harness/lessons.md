### 2026-09-23 — an unpinned JDK made every build cold (the real "hour to build")

### 2026-09-23 — a Gradle check could not run at all with the configuration cache enabled
- Symptom: `./gradlew checkCapabilityManifests` failed with `cannot serialize Gradle script object references`. The capability manifest gate is what feeds the Play Data safety answers, and it had never once run successfully under the factory's own build settings.

- Evidence: the cache report trace read `this$0 → Build_gradle$$$result$1$2 → Field action → VirtualProperty actions → Task :checkCapabilityManifests`. - Change made: `checkCapabilityManifests` is now `CheckCapabilityManifestsTask : DefaultTask()` with `ListProperty`, `Property`, `ConfigurableFileCollection` and `RegularFileProperty` inputs and a `@TaskAction`; every provider read moved to configuration time. ### 2026-09-23 — the factory could not express a repeatable purchase at all
- Symptom: the owner described the monetization he actually wants — an in-app shop selling token or credit packs that a user buys repeatedly, e.g. tokens spent on an AI assistant. The billing capability could not represent that. `Entitlements` was a `Set<ProductKey>` of owned things, there was no balance type, and `PlayBillingController` had **no consume call anywhere**. A pack modelled as an owned entitlement is granted once and, because Play requires a consumable to be consumed before it can be bought again, is then unpurchasable forever. We would have shipped a shop where every product can be bought exactly once.
- Root cause: the capability was designed from the shape of one app — "remove ads or unlock a feature" — and then treated as general. That is the same defect class as a hardcoded error message that drifts from its regex: a single case generalised without checking the cases it excludes. The owner had to name it twice: *"у нас завод, а не конкретное приложение"*. The concrete first symptom was the missing `consumeAsync`, but the real defect was the product model.
- Fix class: model the whole mechanic, not the case in front of us.
- Evidence: `javap` against the real `billing-9.1.0` artifact confirmed the API before any code was written — `ConsumeParams.newBuilder().setPurchaseToken(...)`, `ConsumeResponseListener.onConsumeResponse(BillingResult, String)`, `BillingClient.consumeAsync(ConsumeParams, ConsumeResponseListener)`, and `Purchase$PurchaseState` carrying `PURCHASED`/`PENDING`. Thirty-four billing tests then covered the rules without a device, including the two that would have caught the defect: a consumable credits the wallet and is **consumed rather than acknowledged**, and the same pack bought three times credits three times. `:billing:test :billing:assembleRelease` → `BUILD SUCCESSFUL`, **34 tests, 0 failures, 0 errors** across `PurchaseLedgerTest 11`, `FakeBillingControllerTest 8`, `BillingCatalogTest 7`, `WalletTest 6`, `EntitlementsTest 2`.
- Change made: added `Wallet` (spendable balances, with a spend refused rather than clamped), `ConsumablePack` (grant amount, unit, `Fulfillment` of `LOCAL` or `SERVER_COST`), `PurchaseState`/`PurchaseRecord`/`PurchaseOutcome` mirroring Play without importing Android, and `PurchaseLedger`, which holds the settlement rules in testable code: only `PURCHASED` grants; a consumable is consumed; settlement is idempotent per purchase token because Play re-reports an unconsumed purchase on every cold start; a failure grants nothing so it retries. `BillingController` gained `wallet` and `spend()`. `PlayBillingController` gained the consume call, a `BillingStateStore` (a wallet is **not** recoverable from Play, so losing it loses paid-for credit), and a `PurchaseAuthority` seam required only for `SERVER_COST` packs. The fake settles through the same ledger, so fake tests exercise the real rules rather than a parallel implementation that can drift.

### 2026-09-23 — the worker runner reported DONE for work that was never done
- Symptom: a Codex worker (`remoteconfig`) was launched to build a Firebase Remote Config capability, produced **no files at all**, and `node scripts/codex-run.mjs list` reported it as `DONE last=yes`. It was believed. Only because the authoritative capabilities build printed four `PASS` manifests and no `:remoteconfig:` task — the module was absent from the graph — was the truth found: `capabilities/remoteconfig/` did not exist, `settings.gradle.kts` still listed only `:core, :ads, :billing, :telemetry`, and `capabilityModuleNames` was unchanged. The second worker (`capability-integration`) had the same outcome and was reported `BLOCKED(RATE_LIMITED)`.
- Root cause: three independent defects, all in `scripts/codex-run.mjs`.
  1. **Signal never outranked exit code.** `finish()` computed `meta.status = code === 0 ? 'done' : signal ? 'blocked' : 'failed'`, and `status()` used `rec.exitCode === 0 ? 'DONE' : rec.signal ? BLOCKED(...)`. Both branches put the exit code first, so a run diagnosed with any signal but exiting 0 was reported as `DONE`.
  2. **Diagnosis scanned the entire transcript.** `finish()` ran `diagnose(errText + outText)` over the full stdout log and stderr. That text includes the prompt echo and every file the worker read, and the repo's own documents name the keywords — `AGENTS.md` says `RATE_LIMITED`, `harness/dual-agent.md` tabulates `RATE_LIMITED`/`CONTEXT_LIMIT`/`AUTH_ERROR`. So reading the harness caused the runner to claim the harness had failed. `storekit`'s recorded `CONTEXT_LIMIT` has **no limit text anywhere** in its `.err` or `.log` and was a false positive of exactly this kind; the `cap-ads-billing`, `cap-core`, `scaffold-src` and `scripts` runs, by contrast, do contain a real `ERROR: You've hit your usage limit. Upgrade to Pro` line, so not every signal was wrong.
  3. **Nothing checked that a finished worker changed anything.** A `DONE` label carried no evidence, so "the worker said done" was indistinguishable from "the work exists".
- Fix class: order the signal above the exit code, bound what is diagnosed, and never let a status label stand in for evidence.
- Evidence: `remoteconfig.exit.json` read `{"exitCode": 0, "signal": "AUTH_ERROR"}` while `list` printed `DONE` — a direct contradiction between the record and the label. After the fix the same records print `BLOCKED(AUTH_ERROR)` and `BLOCKED(RATE_LIMITED)`, `node --check scripts/codex-run.mjs` exits 0, and the fix immediately caught the second false `DONE` that the old code had hidden.
- Change made: `DIAGNOSE_WINDOW_LINES = 40` and diagnosis restricted to the tail of stderr plus the tail of the log, so the CLI's own error is read without the prompt echo or the documents a worker opened; `finish()` and `status()` both check `signal` first; `harness/lessons.md` records the finding. Sensor debt: a regression check for the classification belongs in `scripts/selftest.mjs`, but that file is owned by a concurrently running worker, so it is deferred rather than written in a conflict.

### 2026-09-23 - an illustrative example was turned into a product strategy

### 2026-09-25 - a round-trip test cannot validate a conversion constant, and the fixture comment laundered the wrong one as truth

- Symptom: the pure-Kotlin domain layer for `apps/2026-09-25-pipe-sizing` shipped `Units.mbhToKilowatts` as `0.2930711111111111`. The value is wrong by a relative **1.396892871955936e-7**: from the International Table BTU (`1 BTU_IT = 1055.05585262 J`, `1 MBH = 1000 BTU_IT/h`) the value is **`0.2930710701722222`**. The accompanying test asserted only that `kilowattsToMbh(mbhToKilowatts(100.0)) == 100.0`, which a wrong-but-self-consistent factor satisfies exactly, so the suite was green over a wrong constant. Its comment made it worse: `// 100 MBH = 29.307111111... kW` restated the shipped value as an independent fact, so the fixture read as documentation of a checked number.
- Root cause: a round trip tests **invertibility**, not **correctness**. Any constant `k` round-trips through `* k` and `/ k` (up to float error), so the assertion is invariant under replacing `k` with an arbitrary wrong `k'` - the test is blind to precisely the defect it appears to guard. The failure mode is self-concealing in two ways: the round trip passes, and the comment, written by reading the code, certifies the value it was read from. A conversion factor has an external source of truth (a published definition), and nothing in the suite consulted one.
- Fix class: a physical constant needs at least one assertion against a value derived **independently of the implementation**, at more than one magnitude, with a tolerance tighter than the error being hunted. Round-trip assertions are still worth keeping as an additional property, but never as the only check on a constant. Fixture comments must state the derivation and its source, never echo the code - an echoed constant reads as corroboration when it is only duplication.
- Evidence: `0.2930711111111111` vs exact `1000 * 1055.05585262 / 3600 / 1000 = 0.2930710701722222`, relative error `1.396892871955936e-7` computed independently in `node`; the old test passing against it; the fixed test asserting `0.2930710701722222` / `29.307107017222222` / `293.0710701722222` for `1` / `100` / `1000` MBH at `CONVERSION_TOLERANCE = 0.0000000001`, a tolerance ~3 orders tighter than the defect so the old constant fails it.
- Change made: the constant was replaced by a named `MBH_TO_KILOWATTS` carrying the BTU_IT derivation inline and used in both directions; the round trip kept as a secondary assertion; the misleading comment replaced by the derivation. The general rule this incident is an instance of - a check must be able to fail on the defect it names, not merely to pass on the current artifact - is the same one behind the two entries above about guards that validated shape instead of the thing claimed.

### 2026-09-25 - the shipped unit tests included one that could not fail, and its replacement caught a real fixture bug

- Symptom: `selectsOnlyTheInputsRequiredByTheChosenMethod` asserted that `case.method.requiredInputs` equals a set of three enum values, and separately that a case with all inputs present computes. ### 2026-09-25 - a worker's "Access denied" on the Gradle wrapper lock was contention between two workers, not a permissions fault

- Symptom: the `domain-core` worker implemented its files correctly and then reported its verification **blocked**, with `node scripts/verify-slot.mjs --slot pipe-sizing --build` returning `VERDICT: FAIL` on `assembleDebug` and `java.io.FileNotFoundException: ...\gradle-9.7.1-bin.zip.lck (Access denied)`, plus `scripts/run-slot-tests.mjs` not yet existing. Re-running the identical gates on a quiet machine minutes later: tests `15 tests, 0 failures`, and `VERDICT: PASS - available checks green` including `PASS assembleDebug`.

Gradle takes an exclusive lock on the wrapper distribution while it unpacks and uses it, so the concurrent invocation fails on `.lck`. The message misleads: `Access denied` reads as an ACL or read-only fault, but both lock files on disk are zero-length with ordinary `Archive` attributes - the fault was a second holder, not permissions. Nothing in the factory serialises Gradle across parallel workers.
- Fix class: a shared `GRADLE_USER_HOME` makes Gradle builds a **serial resource**, so parallel workers must not overlap on it - either serialise build-bearing tasks or give each worker its own home. When a gate FAILs on a lock file, check whether another build is running before touching permissions, and treat a worker that reports `DONE` while its own gate said `FAIL` as **unverified**: re-run the gate on a quiet tree rather than accepting or rewriting the work.
- Evidence: the worker's `VERDICT: FAIL` on `gradle-9.7.1-bin.zip.lck (Access denied)` while its report claimed correct code with a clean suspicious-literal scan; `Get-ChildItem` showing both `.lck` files present, `len=0`, `attrs=Archive`; `$env:GRADLE_USER_HOME=E:\Programm\Android\.gradle`; then the same two commands passing after both workers finished.
- Change made: the code was verified rather than rewritten, and every Gradle gate in this session was run only after the ledger showed no worker running. The serialisation gap itself is unfixed and recorded here, because the symptom presents as an infrastructure fault and will otherwise be misdiagnosed as a broken toolchain or filed against the wrong worker.
- Addendum, same day: the contention is **bidirectional**, and the second occurrence was self-inflicted. While the `ui-wave` worker was implementing, the orchestrator ran `publishToMavenLocal`, two `gradlew :app:dependencies` resolution probes and a `verify-slot --build` on the same `GRADLE_USER_HOME`; `ui-wave` then reported its tests and build blocked on the same `.lck` and closed with a truthful but unverified result. Running the identical gates on the now-quiet machine gave `14 tests, 0 failures` and `VERDICT: PASS`. So a `BLOCKED`/`FAIL` report from a worker needs the question **"was anything else building?"** asked in both directions - the orchestrator holds the lock just as readily as a peer worker, and scheduling a gate against a running build-to-order pair manufactures the very failure it then has to diagnose.
- **Correction, after a controlled comparison: contention explains the first two occurrences but not the rest, and is not the dominant cause.** Four separate workers (`domain-core`, `harness-caps`, `spec-gaps-2`, `store-pack`) each reported Gradle blocked on the same `.lck`, including runs where the orchestrator was provably **idle** - in the last case the orchestrator had been sleeping in a poll loop for the entire worker run and had issued no Gradle command. Within the same minute that the worker reported `access denied`, the orchestrator's own `verify-slot --strict-store --build` on the same slot returned `PASS assembleDebug` and `VERDICT: PASS`. Machine, slot and wrapper distribution identical; the only variable is which process ran it. Corroborating evidence from the same worker session: an isolated `GRADLE_USER_HOME` "attempted to download Gradle 9.7.1 but **network access was denied**", and the worker could not delete its own ignored cache directory because "this environment rejected the exact scoped recursive deletion command". Together those indicate the worker runs in a **restricted sandbox with no write access to the shared Gradle home and no network**, so Gradle cannot take its distribution lock no matter how quiet the machine is. The blocker is the environment, not a peer or the orchestrator - and the misleading part is that `Access denied` on a lock file reads as contention or as an ACL fault on the toolchain.
- Change made: **every Gradle-based gate in this milestone was run by the orchestrator, and a worker's Gradle result is treated as unverified by default.** The correct reading of a worker report here is that its source changes may be complete while its gate result carries no information, so the orchestrator re-runs `run-slot-tests.mjs` and `verify-slot --build` itself on every landing - which is how the compile break and the wrong-unit conversions in the `spec-gaps-2` output were found. The honest worker behaviour is what `store-pack` did: report `VERDICT: UNVERIFIED` rather than claim a pass it never observed. The structural fix - giving workers a writable per-worker Gradle home, or routing all builds through a single orchestrator-side queue - is **not implemented** and is the reason this section exists.
