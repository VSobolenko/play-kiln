# Production Android / Compose stack for Plinth

**Snapshot:** 2026-10-17. **Scope:** repository and dependency inventory plus AndroidX/vendor documentation and Maven metadata. This is a research and implementation-priority note, not a claim that “enterprise apps all use” any particular library. “Production-ready” here means stable, maintained platform/library capabilities with a demonstrated Plinth use case, verified dependency/version fit, and no unnecessary parallel framework.

## Evidence labels

- **MEASURED** — read from the current slot files or a version-specific artifact during this pass.
- **ON RECORD** — stated by AndroidX, a library maintainer, or Maven metadata.
- **INFERRED** — an engineering recommendation from those observations.
- **UNVERIFIED** — needs a build, device exercise, or live behavior measurement.

## 1. Reinvention-risk inventory in Plinth

This is a targeted inventory, not a judgement that all bespoke UI is wrong. The slot has already adopted Compose, Material 3, Navigation 3, Coil and Foundation. The risks are local places where a custom layer duplicates an existing system component, or where the app has not yet chosen a coherent policy over APIs it already has.

| Measured surface | Evidence in Plinth | Platform/library capability | Risk / opportunity |
|---|---|---|---|
| **Navigation host and motion** | `ui/PlayKilnApp.kt:198,304` owns a typed `rememberNavBackStack` and one `NavDisplay`; `:304-320` supplies no `transitionSpec`, `popTransitionSpec` or `predictivePopTransitionSpec`. Catalog `navigation3 = "1.1.7"` (`gradle/libs.versions.toml`). | NavDisplay already owns scene-change transitions and predictive back; the current AndroidX stable is Navigation 3 **1.2.0**. Explicit host/scene specs can make the forward, pop and predictive paths intentional. | No evidence that Plinth reimplemented the back stack or transition engine. The risk is an implicit default motion policy and a dependency pin one stable release behind. Pick one restrained motion language, test all three directions, and preserve Nav3 as the one navigation engine. |
| **Bottom navigation chrome** | `ui/PlayKilnApp.kt:286-301` selects a custom bottom bar or rail based on window width. `ui/components/PlinthNavBar.kt:33-82,132-161` draws the bottom surface, tab icon/label, selection colors, hit region, and create FAB itself. | Material 3 `NavigationBar` / `NavigationBarItem`; Material adaptive `NavigationSuiteScaffold` can choose bar/rail presentation from window configuration. | The wide-window rail already uses Material `NavigationRail` / `NavigationRailItem` (`PlinthNavBar.kt:92-127`); the compact bar reimplements the component. Keep the branded FAB and palette if desired, but prefer M3 item semantics/indicator and let the adaptive suite own form-factor switching rather than growing another breakpoint shell. This is an improvement candidate, not proof the custom styling is defective. |
| **Top app bar** | `PlinthTopBar.kt:24-55` uses Material 3 `TopAppBar` and `TopAppBarDefaults`. | Material 3 component already. | Low reinvention risk; retain the slot-owned title/balance treatment. |
| **Studio and list surfaces** | `ui/home/HomeScreen.kt:129` uses Foundation `LazyVerticalGrid`; `:205,223` use `LazyRow`. `ui/home/HomeSceneStrip.kt:124,140` uses `LazyRow` and `Modifier.animateItem`. `ui/batch/BatchScreens.kt:276,309` also uses `animateItem`. | Foundation lazy grids/lists, item animations, Foundation Pager and snap behavior. Paging Compose is already on the classpath. | These are already standard lazy primitives, not a hand-written list engine. Do not add Snapper or a “smart list” framework. The home grid can still be made more image-led and visually composed; that is product styling/content, not a missing list library. Use Paging only if the local library actually needs incremental loading at its measured data size. |
| **Per-item motion** | `ui/home/HomeSceneStrip.kt:209,217` animates selection scale and color; `ui/autocard/FormingCardPreview.kt:62,113` animates skeleton alpha and content state. | Compose animation APIs and Material 3 `MotionScheme` provide reusable transition specs; `Modifier.animateItem`, `AnimatedContent` and `AnimatedVisibility` cover common cases. | These are legitimate app-specific state transitions, but their specifications are locally chosen. Centralize common timing/physics and respect reduced-motion preferences; avoid replacing purposeful progress or result feedback with decorative motion. |
| **Loading state** | `ui/PlayKilnApp.kt:672-685` uses a generic `CircularProgressIndicator` default in `WithLoadedDestination`; `:690-712` has a custom `ProjectImageState` state machine for a file-backed domain image. Home and thumbnail image loading/error slots are written per surface (`ui/home/HomeScreen.kt:281-305,416-433`). | Material 3 progress indicators; Coil Compose's `AsyncImage`/`SubcomposeAsyncImage` state slots; Compose transitions for state-to-state changes. | The repeated visual placeholder/error treatment can be shared and made result-shaped. Do not remove the explicit loading/failure distinction: it's truthful domain state. A generic spinner is appropriate for indeterminate work, but not a substitute for actual job progress or a finished-output preview. Coil does not replace the pixel/domain loader used by the editor/compositor. |
| **Image loading** | `coil-compose` **3.6.3** is declared. `HomeScreen.kt:281,416`, `LibraryScreen.kt:327`, `SelectedMediaPreview.kt:45`, and `GroupScreen.kt:396` use `SubcomposeAsyncImage`; `CoachScreen.kt:667` and `ListingTextScreen.kt:310` use `AsyncImage`. | Coil already provides local image requests, decode/caching, Compose integration and state callbacks. Coil docs distinguish ordinary `AsyncImage` from cases needing subcomposition. | Not a from-scratch loader. Prefer `AsyncImage` for simple thumbnails when the current placeholder is enough; reserve `SubcomposeAsyncImage` for a genuine state-specific composable. Keep a single shared Coil stack and test high-resolution local images/memory pressure. No Coil network adapter is declared; add one only for actual remote image URLs, not because OkHttp exists. |
| **Custom image/domain decode** | `ui/PlayKilnApp.kt:697-712` calls `ProjectImageLoader(ProjectRepository(context)).load(photoId)` on `Dispatchers.IO`; the editor uses `ProjectImage`/pixel-buffer values. | Coil is a presentation image loader; CameraX/Android image APIs serve capture; domain pixel/compositor code owns original-pixel fidelity. | This is not automatically reinvention. Do not route fidelity-sensitive editor/export pixels through a thumbnail loader. Audit only if the custom path duplicates routine thumbnail decode/caching. |
| **Adaptive scene layout** | `ui/PlayKilnApp.kt` imports `rememberListDetailSceneStrategy`; `NavDisplay` passes it at `:310`, while its `ListDetailSceneStrategy.detailPane()` metadata is assigned per entry. | Nav3 scene strategies and Material adaptive Navigation 3 (already declared) provide scene/list-detail behavior. | Prefer scenes/strategies over hand-maintaining a second route-to-layout engine. Confirm on compact and expanded widths that the entries marked as detail actually produce the intended list/detail composition; a strategy being declared is not evidence the UX works. |

**MotionScheme source conflict resolved for this snapshot.** `ai-visual-language.md` §2.1 says the pinned Material 3 1.4.0 does not expose `MotionScheme`; `modern-ai-android-2026.md` §2 says it is available. I inspected the versioned `androidx.compose.material3:material3:1.4.0` sources JAR: it contains `MotionScheme.kt`, but the interface and related implementations are `internal`. Therefore the file's presence does **not** make it a public API an app can call. AndroidX lists 1.4.0 as stable and 1.5.0-beta01 as the newer prerelease. The current unversioned API reference is not sufficient evidence that Plinth's 1.4.0 pin exposes it. For this pinned production app, treat public Material 3 `MotionScheme` as **not available** until a versioned stable API proves otherwise; use the public Compose animation specs with shared app-level motion tokens in the meantime. This makes the earlier `ai-visual-language.md` conclusion correct for the current pin and supersedes the contradictory claim in `modern-ai-android-2026.md`.

## 2. Production stack map — choose stable capabilities, not prestige dependencies

The evidence below is vendor/API documentation about supported capabilities. It does **not** establish that named commercial apps use the same internals.

| Concern | Recommended production pattern for Plinth | Plinth status and fit |
|---|---|---|
| **Design-system components and motion** | Keep Compose BOM-managed Foundation, Compose animation and Material 3 as the default component/motion layer. Use slot-owned colors, type and shapes with M3 controls; centralize stable `spring`/`tween` specs for bounds and effects. Adopt Material 3 `MotionScheme` only when the public API is available in a stable version allowed by the dependency policy. | **Already present:** BOM `2026.09.00`, Compose UI `1.12.0`, Material 3 `1.4.0`. |
| **Navigation and scene layout** | Use one typed Navigation 3 back stack and `NavDisplay`; use `transitionSpec`, `popTransitionSpec`, and `predictivePopTransitionSpec` for explicit global motion, with metadata overrides only for genuine scene exceptions. Use Nav3/M3 adaptive scene strategies for list-detail or supporting panes; use `NavigationSuiteScaffold` for bottom-bar/rail form-factor changes where it matches the product shell. | **Already present but needs polish:** Nav3 `1.1.7`; stable `1.2.0` is on AndroidX release notes (2026-09-23). List/detail strategy and adaptive Navigation 3 module are present. `NavigationSuiteScaffold` is not currently in source; `material3-adaptive-navigation-suite` stable `1.4.0` (Maven metadata; `1.5.0-beta01` also exists). |
| **Cross-screen image continuity** | For a user photo that stays the same object between library → editor/result, use `SharedTransitionLayout` with `sharedElement` or `sharedBounds` and stable item IDs. Keep unrelated surfaces out of the transition; test cancellation and Predictive Back. | **Not present in source search.** It is built on Compose animation, not a separate Maven library. It is a premium polish candidate for a small number of image journeys, not a blanket animation rule. |
| **Image loading and caching** | Use Coil Compose for asynchronous user/project image display, with deterministic placeholder/error behavior and stable request keys. Use `AsyncImage` by default; subcompose only when a composable loading/error slot is actually needed. Separate previews/thumbnails from original-pixel editing/export. | **Already present:** Coil Compose `3.6.3`. |
| **Long / growing local collections** | Use Room/Flow + Paging when dataset growth makes whole-list materialization or query cost a demonstrated issue; Paging Compose integrates with lazy layouts and exposes load/error/retry states. For small bounded collections, a normal keyed lazy list is simpler. | **Already present:** Room `2.8.5`, Paging runtime `3.5.3`, Paging Compose `3.5.1`. This is capability inventory, not a mandate to page every list. |
| **Durable asynchronous work** | WorkManager for uploads, retries, long-running or restart-resilient jobs whose contract is to continue after leaving the screen/restarting. Keep short-lived UI transformations in structured coroutines when they may safely stop with the process. Surface queued/running/succeeded/failed states from the work source of truth. | **Already present:** WorkManager `2.12.0`; the slot also has batch and delivery workers. Avoid implementing a second durable scheduler. |
| **First-launch and interaction performance** | Baseline Profile journeys should represent actual Plinth flows (launch → Studio, import → compose, inspect → export). Generate with Macrobenchmark on a device/emulator, then compare release-like startup/frame metrics; a profile is evidence only for paths it covers. | **Already wired:** Baseline Profile plugin `1.5.0`, Profile Installer `1.4.1`, Macrobenchmark `1.4.1`, `:baselineprofile`, and profile task. Android docs report “about 30%” improvement for included code paths generally; this is not a promised Plinth result. |
| **Capture and coaching** | CameraX use cases and lifecycle binding for a live camera preview/capture flow; keep gallery/file imports through the Photo Picker where appropriate. CameraX exists to absorb device-specific camera behavior, rather than build preview/capture lifecycle plumbing manually. | **Already present:** CameraX `1.6.2` core/camera2/lifecycle/view. Use for the Coach capture workflow; no new camera stack. |
| **Home-screen widget** | Glance only if there is a concrete glanceable action/state, such as batch completion or next queued job, with a meaningful update policy. A widget is a separate remote surface; Compose app screens cannot simply be reused wholesale. | **Not present; defer:** no demonstrated widget job or user requirement in current Plinth scope. |
| **UDF/state architecture** | Keep screen state as observable UI state from ViewModels/repositories and navigation as Nav3. Add an architecture framework only to resolve a measured state/navigation problem, not to signal “enterprise.” | **Already has ViewModels/StateFlow patterns.** Circuit is an alternative app architecture, not a Nav3 animation or scene plugin. |
